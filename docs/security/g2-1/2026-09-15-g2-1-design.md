## 2. Recorte escolhido e por que ele inclui criação

**G2-1 propõe fechar cinco operações existentes:** `geoOverride.createRule`, `getRule`, `updateRule`, `deactivateRule`, `reactivateRule`, junto de seus cinco helpers. Acrescenta **duas adaptações mínimas de chamadores da criação**: `geoOverride.seedCoastalRules` e `server/seed.ts`.

São **três arquivos de produção**, **cinco operações CRUD completas**, **seis rotas tRPC tocadas** (uma delas é adaptação parcial de seed), mais a entrada operacional `server/seed.ts`. Não confundir esses números com as 13 rotas diretas, duas outras rotas que leem regras, duas entradas de pipeline e o seed medidos para a família.

O corte inicial de quatro pontos por ID foi retirado antes da implementação: embora suas chamadas fossem locais ao router, `createRule` continuaria gravando NULL. A correção tornaria uma regra nova inacessível ao próprio criador. A prova deve percorrer **criar → consultar → editar → desativar → reativar**, além das fixtures próprias preexistentes. A autorização de bloquear legado NULL não é usada para justificar fabricar novo NULL.

Alternativas consideradas:

| Alternativa | Disposição |
|---|---|
| Apenas ponto get/update/toggles | Rejeitada como entrega funcional independente: rompe o ciclo novo de criação. |
| Cinco operações CRUD + passagem de tenant nos dois callers de create | Recomendada: preserva o ciclo próprio, fecha todas as chamadas dos helpers alterados e não exige resolver visualização/logs/seed completo. |
| Toda a família G2 num patch | Adiada: agrega contratos distintos de histórico, pipeline, UUIDs e seed, tornando a prova e a revisão menos delimitadas. |

**Claim candidato:** nas cinco operações CRUD nomeadas, tenant ausente não alcança o negócio; uma regra nova recebe o owner confiável; A só consulta ou altera regras A; B, NULL e inexistente são indisponíveis; papel admin não ultrapassa ownership; payload não altera owner/id/timestamps; leituras de autorização, escrita e verificação final dos writes ficam numa transação. O comportamento independe de `TENANT_STRICT`.

**Não é claim de confidencialidade de G2 inteiro:** `listRules`, stats, resolução, logs e outros consumidores ainda têm lacunas. A listagem global remanescente pode revelar uma regra que getRule passa a negar. Esses caminhos continuam bloqueios da família e da avaliação B2/PR #9. Nenhum GO parcial pode omitir esse fato.

## 5. Persistência, atomicidade e audit

Privados permanecem no módulo existente. Usar um handle tipado de select/insert/update do DB/tx, sem qualquer tenant opcional. Uma função de leitura recebe handle, tenant, id e intenção de lock; aplica `AND(tenant_id = owner, id = target)`, limit 1, verifica ID/owner retornados e não filtra por active.

**Get:** validar contexto → obter DB → SELECT estrito → confirmar identidade → retornar row/null. Nenhuma consulta global antecede esse SELECT.

**Create:** validar contexto e sanitizar payload → obter DB → uma transaction → INSERT com owner forçado e RETURNING id → exigir um ID válido → SELECT estrito desse ID no mesmo tx → confirmar ID/owner → devolver row confirmada → commit → audit. Falha de RETURNING/readback aborta a transação e a criação falha com erro interno genérico; não retornar row indefinida nem uma criação aparente. Sem reconciliação ou retry automático.

**Update/toggles:**

1. Validar contexto, normalizar identidades e sanitizar patch; obter DB.
2. Uma transaction; SELECT estrito com **FOR UPDATE** e captura de before. Se indisponível, lançar sinal privado de negação.
3. Para patch vazio autorizado, retornar before com `didWrite: false`.
4. UPDATE com whitelist **e predicate final id+tenant**, RETURNING id. Exigir exatamente um ID correspondente; zero linhas não é sucesso mesmo se uma leitura posterior ainda encontra a row antiga.
5. SELECT estrito no mesmo tx; exigir identidade/owner correspondentes. Se isActive foi solicitado, exigir o boolean observado. Retornar before/after reais; não fabricar after mesclando patch.
6. Erro de verificação lança dentro do tx para rollback. Capturar **somente** a classe privada de negação/verificação e traduzir para null/false; erros SQL desconhecidos propagam.
7. Depois do commit, se didWrite, aguardar audit com snapshots em memória; retornar row/true. Nenhum novo getDb/readback do negócio depois do commit.

FOR UPDATE mantém before imediatamente anterior ao write sob escritores concorrentes da row; não substitui predicate ou readback e não promete serialização de todo o domínio. A API `.for()` foi encontrada na declaração instalada de Drizzle; compatibilidade de tipos será verificada na execução futura. Não usar SKIP LOCKED/NOWAIT. Não prometer proteção contra triggers diferidos arbitrários ou semântica de FKs não ensaiada.

Audit mantém actions `geo_override.create/update/deactivate/reactivate`, tableName `geographic_overrides`, recordId real, **userId:null** e operatorId legado no after. Create usa before ausente e after `{...rowConfirmada, operatorId}`; os demais usam before real e after equivalente. Não emitir sucesso em negação ou rollback; patch vazio não finge alteração.

**Limite aceito para proposta:** audit é aguardado **após** o commit do negócio. O serviço atual pode retornar NULL; preservar a resposta de negócio e registrar esse resultado como não confirmado nas provas, sem novo envelope/exceção/retry. Um throw inesperado que escape pode propagar após o dado estar committed. Não declarar rollback retroativo nem audit durável. O teste de sink controla a chamada/ordem/payload; não comprova persistência real de audit_logs. Não alterar audit.ts ou adotar outbox neste recorte.
