**Local candidate, not an enabled writer.** This directory is deliberately outside

## Normative disposition still pending

literal `db.transaction()`. This SQL candidate implements the durable atomic
semantics required by ADR-002 item 10 but does not call those TypeScript methods.
No statement here ratifies their substitution. Before enabling this exact writer,
the responsible party must reconcile those two literal requirements specifically
for `intake.create(newProject)` via its named Data API transaction. The existing
direct helper, its audit calls and other writers retain their current contract.

## Operation and wire

Existing operation: `intake.create`, only its `newProject` branch. One client,
one project in `intake`, one intake in `draft`, three durable create audits.
No existing project/client/lead target, membership, scope, estimate, financial
calculation, geocode, approval, version, export or other business DML is enabled.

Named endpoint: `POST public.structr_intake_create_v1(preimage text)`. Body is
`{preimage}`; callers cannot choose a schema, table, function, role or SQL.
The Node side produces the exact legacy `JSON.stringify({...validatedInput,
tenantId,userId})` bytes after the existing router schema has parsed its input.
Defaults, key order, UUID casing, omitted/null fields and numeric serialization
are not rewritten before SHA-256. SQL validates that same representation and
compares both embedded identity values with protected current identity; embedded
identity is not an authorization source. No client-supplied hash is accepted.

The new channel permits at most 65,536 UTF-8 bytes and sixteen nested containers,
including the root object. Scalars do not add a container level. Duplicate keys
are checked recursively with PostgreSQL `IS JSON OBJECT WITH UNIQUE KEYS` before
conversion to JSONB; NUL, invalid surrogates and unrepresentable JSON are refused.
Every numeric value must also parse to a finite IEEE-754 response value. Overflow
such as `1e1000` is refused before business DML; finite rounding, subnormals,
underflow to zero and integers outside JavaScript's safe-integer range remain
accepted. This check does not rewrite the preimage, restrict numeric precision
stored in JSONB or perform a financial calculation.
The complete normalized schema is independently checked in SQL: closed root and
newProject/client objects, current enums, required fields, null/absence rules,
UTF-16 string lengths, ECMAScript trim and the installed Zod4 email/UUID grammar.
`rawPayload` stays inert JSON under its own key. The wire limits do not change the
direct helper's contract.

Response:

```json
{
  "version": "structr-authenticated-intake-create-v1",
  "context": { "actorId": "protected profile UUID", "tenantId": "protected tenant UUID" },
  "intake": {
    "id": "request UUID", "tenantId": "protected tenant UUID", "leadId": null,
    "projectId": "new project UUID", "status": "draft", "formData": {},
    "createdAt": "UTC timestamp with milliseconds", "updatedAt": "UTC timestamp with milliseconds"
  }
}
```

Replay returns the **current** eight-column intake; status/linkage/formData may
have legitimately evolved. It does not require the original client/project or
audit snapshots to be unchanged and does not merge formData into the row.

## Authorization, atomicity and retries

The Data API verifies the bearer signature. The RPC reuses protected bounded-JWT
claims, profile/tenant resolution and RBAC helpers inside a serializable read-write
transaction. Lock order is config, profile, tenant, role/grants/permissions, legacy
advisory tenant/request, then replay intake. Claims are rechecked after waits,
before initial DML and after final readback. No Auth-session liveness promise is
made beyond the existing bounded token and current organizational revocation.

Admin passes in its own tenant. Otherwise client:write passes; other client:*
without write denies; no client:* remains unenforced and allowed as in the direct
router. A different tenant can create only in its own organization. No membership
is required for a project that does not yet exist.

Every new business row is compared with the validated intention and expected
database defaults. The real project provenance trigger must yield formation_only.
Audits store all 21 client, 55 project and 8 intake fields in the legacy camelCase
representation, with dates as canonical UTC milliseconds and numeric columns as
Drizzle strings. After all audits, the RPC rereads the just-created rows and its
three audit IDs and verifies them against immutable captured evidence. Missing,
suppressed, changed or failed audit/readback causes rollback of every row.
Each audit ID is bound to its specific event tuple, with NULL-safe comparisons;
three copies of one event cannot replace the three required distinct events.
`SET CONSTRAINTS ALL IMMEDIATE` runs before final readback so a late constraint
trigger cannot defer a changed row until after this comparison. This is a
transactional readback, not a post-commit attestation against arbitrary DBA changes.

Replay hashes the original text, reauthorizes and returns the current tenant-owned
intake only if the stored creationFingerprint matches. A stable conflicting key
or payload yields `INTAKE_FORMATION_CONFLICT` without a write. Another tenant's
global key collision reveals no row data. Serializable snapshots are not refreshed
by advisory-lock waits: only a unique violation from the actual intake INSERT with
schema `public`, table `intake_forms`, constraint `intake_forms_pkey` maps to 40001.
That exception aborts the entire operation. No other 23505 is retried. The transport
retries the entire HTTP request at most three times only for 40001/40P01; domain
conflicts and uncertain network results never cause automatic resubmission.

Nominal errors: `FORBIDDEN`, `INTAKE_FORMATION_INPUT_INVALID`,
`INTAKE_FORMATION_CONFLICT`, `INTAKE_FORMATION_INTEGRITY_VIOLATION`. Unexpected SQL
errors are sanitized by the RPC; raw driver details or personal data are not returned.

## Exact authority

Dedicated owner `structr_intake_create_owner_v1` has NOLOGIN, NOINHERIT,
NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS; no table ownership
or API-assumable membership. Existing readers do not become writers.

- Lock relations: only the selected identity/config/RBAC columns plus UPDATE(id).
- clients: eight INSERT columns, 21 enumerated SELECT columns.
- projects: fourteen INSERT columns, 55 enumerated SELECT columns.
- intake_forms: six INSERT columns, eight SELECT columns, UPDATE(id) for replay SHARE.
- audit_logs: eight INSERT columns, ten enumerated SELECT columns.
- No table-wide grants, DELETE, UPDATE of business values, sequences or auth.* access.
- Exactly two owner-specific config policies: SELECT true and lock UPDATE true with CHECK false.
- Four existing INVOKER helpers: claims, UUID, permissions, projection. Three new
  private functions: string validation, preimage validation and fixed writer body.
- Authenticated receives nominal EXECUTE on the public wrapper and bound private
  body, but no private schema USAGE or raw table access. Wrapper is INVOKER VOLATILE
  with serializable configured as in existing boundary migrations.

Preflight refuses unreviewed exposed ACLs/functions/views/role paths, missing
identity indexes or provenance trigger, deferred request primary keys, deferred
user-defined business triggers, incomplete row shapes and RLS drift on the inspected relations.
The candidate supports the actual contained baseline rather than silently changing
other consumers' policies. Temporary ownership-transfer CREATE/SET grants are
withdrawn before commit. A non-superuser migration suite proves the lifecycle and
compares the actual column/function ACL delta, not a count inferred from this prose.
Preflight describes the catalog at installation. Later authorized DDL is still a
review responsibility; an untrusted DDL-capable principal is outside this boundary.
The runtime constraint barrier additionally catches deferred mutations introduced
after installation before returning the new formation.

## Local proof and limits

Lab files: `server/adr002-intake-formation-physical.test.ts`,
`server/adr002-intake-formation-migration-physical.test.ts` and synthetic formation
fixtures. The harness accepts no database URL or inherited PostgreSQL credentials.
Business physical application additionally requires `ADR002_INTAKE_FORMATION=1`
and `ADR002_INTAKE_APPLY=1` plus the explicit minimum-read baseline.

Initial functional RED: valid ES256 session passed, formation/replay returned 404
for the absent RPC. Expanded refusal/projection/migration RED and subsequent GREEN
results are recorded separately by the runner. Only actual final test outputs may
be reported as completion evidence; default pnpm test skips these opt-in suites.

The numeric review found a concrete recovery defect: PostgreSQL accepted `1e1000`
and committed a row whose response became Infinity for a JavaScript consumer. A
behavioral RED reproduced that defect. The parser now refuses overflow with
`INTAKE_FORMATION_INPUT_INVALID` before any business write. Physical tests compare
all four business/audit row counts on rejection and prove exact-byte fingerprints
and replay for finite upper bounds, subnormals, underflow and non-safe integers.
The strict Node decoder remains unchanged.
